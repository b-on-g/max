# Роли и сценарии

Кто что может в «Заявках в УК через MAX» и как это проверить. Всё, что ниже, работает
и без токена MAX в тестовом режиме `DEV_SKIP_VALIDATION=1`.

## Роли

| Роль | Кто это | Что может | Как получить |
| --- | --- | --- | --- |
| Житель | Любой, кто открыл бота | Подать заявку, приложить фото, поддержать заявку соседа, смотреть заявки и новости своего дома, сменить свой дом в профиле, где показаны его фото, имя, ник и ID из MAX | Открыть бота. Ссылка или QR с кодом дома сразу привязывает дом |
| Диспетчер | Сотрудник УК, закреплённый за домами | Всё, что житель, плюс по своим домам: видеть заявки, менять статус, печатать QR, публиковать новости и отключения | Админ добавляет его по коду сотрудника из профиля и выбирает дома |
| Админ | Руководитель УК или тот, кто разворачивает систему | Всё, что диспетчер, плюс: заводить дома, добавлять сотрудников с ролью | Открывает бота по ссылке-приглашению `https://max.ru/t6_hakaton_max_bot?start=staff_<STAFF_SECRET>`. Дальше админов добавляют другие админы |
| Организация | АДС, РСО, город, участковый | Получать свои заявки и менять статус через API | Ключ в `ORG_KEYS` бота, `openapi.yaml` |
| Бот | Node-процесс на сервере | Проверяет подпись MAX, регистрирует заявки, считает ответственного и срок, шлёт уведомления, хранит базу. В чате отвечает на `/start`, `/help`, `/id`; в групповом чате только на команды, упоминание и слова про заявку, при добавлении здоровается кнопкой «Подать заявку» | `docker compose up` |

Доверие считается ключами, а не логинами: записи о сотрудниках в `Staff` принимаются,
только если их автор сам доверенный админ, и цепочка начинается с ключа бота. Статус
заявки читается только от ключей бота и сотрудников, житель его подделать не может.

У жителя один текущий дом, сменить можно в профиле. Диспетчер видит только дома, которые
ему закрепил админ, админ видит все дома.

## Сценарии

### Житель подаёт заявку

1. Открывает бота в MAX, жмёт «Подать заявку». Если пришёл по QR с подъезда, дом уже выбран.
   Можно и просто написать боту проблему текстом: он спросит «Создать заявку?», и по «Да»
   откроет форму с этим текстом в подробностях. Фото, видео или кружочек в чат работают
   так же: бот скачивает файл, а в форме он уже приложен, лишнее убирается крестиком.
2. Выбирает, где проблема: в доме, во дворе, в городе. Список категорий меняется.
3. Выбирает категорию, для дома указывает подъезд, пишет место, подробности, по желанию фото.
4. Если по этой категории в доме уже есть открытая заявка, приложение показывает её и
   предлагает поддержать вместо новой.
5. Жмёт «Отправить». Незаполненные обязательные поля подсвечиваются только после этой попытки.
6. Бот регистрирует заявку и присылает в чат номер, ответственного, срок реакции и устранения,
   основание. В приложении открывается карточка.

Куда уходит заявка, решает категория: у каждой записан ответственный (УК, АДС, РСО,
муниципальная служба, участковый), сфера и норматив. Житель адресата не выбирает.

### Сосед поддерживает заявку

1. Раздел «Дом», вкладка «Заявки», поиск по категории, подъезду, месту, тексту.
2. Открывает заявку, жмёт «Тоже беспокоит». Голос записывается его ключом, второй раз
   не засчитывается.
3. Организация видит число голосов в API, диспетчер в списке.

### Диспетчер ведёт заявки

1. Раздел «Диспетчер»: пять последних открытых заявок своих домов с выпадающим статусом:
   зарегистрирована, принята, в работе, выполнена, отклонена. Кнопка «Все заявки» открывает
   полный список с поиском и фильтром по статусу.
2. Смена статуса пишется ключом диспетчера, бот замечает её и уведомляет автора в чат.
3. Ниже QR выбранного дома с кнопкой «Распечатать QR» и форма новости или отключения.

### Организация передаёт, оспаривает и эскалирует

1. Ответственный по умолчанию берётся из категории. Организация, у которой заявка сейчас,
   может передать её другой через `POST /org/transfer` с причиной, а диспетчер УК то же
   самое делает выбором «Ответственный» в строке заявки. Житель получает сообщение
   «Передана: …», в карточке видно, от кого пришла.
2. Получившая организация может оспорить передачу через `POST /org/dispute` с причиной,
   заявка возвращается прежнему ответственному, в логе запись «Передача оспорена».
3. Эскалация: `POST /org/escalate` или статус «Эскалирована руководству УК» у диспетчера.
   Житель может сам запросить эскалацию кнопкой в карточке, когда срок по нормативу прошёл:
   у диспетчера такая заявка поднимается наверх с пометкой «Житель просит эскалации».
4. Категория «Другое в доме», «во дворе», «в районе» для случаев, которых нет в справочнике:
   ответственный УК или муниципальная служба, срок 30 дней по 59-ФЗ, диспетчер уточняет.

### Организация работает через API

```sh
curl -s https://<бот>/org/tickets -H 'Authorization: Bearer <ключ>'
curl -s -X POST https://<бот>/org/status -H 'Authorization: Bearer <ключ>' \
  -H 'content-type: application/json' \
  -d '{"ticket":"<link>","status":"done","note":"Лифт запущен"}'
```

Организация видит только заявки своего ответственного, статус чужой заявки ей не дадут.

### Админ смотрит статистику

Кнопка «Статистика по домам» в разделе «Админ» открывает экран с фильтром по периоду
(7, 30, 90 дней, всё время) и по дому. Сводка: заявок за период, открытых, просроченных
по нормативу, выполненных, среднее время до первой реакции, голосов соседей. Ниже
разбивка по ответственным организациям и по домам. Это те же метрики, что предлагаются
для пилота.

### Админ смотрит интеграции

Блок «Интеграции организаций» в разделе «Админ» показывает по каждому ответственному, выдан ли ключ API
(`ORG_KEYS`) и когда организация последний раз ходила за заявками. Так видно, кто
подключён по-настоящему, а чьи заявки пока закрывает диспетчер вручную.

### Админ заводит дом и сотрудников

1. Открывает бота по ссылке-приглашению с `STAFF_SECRET` один раз, получает роль админа.
2. Раздел «Админ», блок «Новый дом»: вводит адрес, код дома для ссылки и QR
   образуется сам, например `pushkina10`.
3. Блок «Сотрудники»: просит коллегу открыть профиль и прислать «Код сотрудника»,
   вводит код, выбирает роль и дома диспетчера, жмёт «Добавить сотрудника». Коллега при
   следующем входе получает роль и свои дома. Ссылку-приглашение админа и её QR можно
   переслать вместо кода, но она даёт роль админа.

## Проверка без MAX

- `#!user=7` открывает приложение от имени тестового пользователя с этим ID.
- `#!start=staff_<секрет>` даёт роль админа, как ссылка-приглашение.
- `#!start=house_<код>` привязывает дом, как QR с подъезда.
- `#!bot=host:port` указывает адрес бота при запуске с дев-сервера. `#!user=7` на проде даёт демо-жителя без MAX: ID до 999 бот принимает без подписи, настоящие ID только с подписью.

## Переменные окружения

| Переменная | Кому | Зачем |
| --- | --- | --- |
| `BOT_TOKEN` | Бот | Токен из MAX, без него нет уведомлений и проверки подписи |
| `BOT_NAME` | Бот | Имя бота для ссылок и QR, иначе берётся из Bot API |
| `STAFF_SECRET` | Админ | Секрет ссылки-приглашения |
| `UK_STAFF` | Админ | Запасной путь: ID пользователей MAX, которые сразу админы |
| `ORG_KEYS` | Организации | Ключи API вида `ads:ключ,municipal:ключ` |
| `APP_URL` | Бот | Адрес мини-приложения для кнопок в чате |
| `DEV_SKIP_VALIDATION` | Тесты | `1` пропускает проверку подписи |
| `MAX_DOMAIN` | Прод | Домен для сертификата Caddy |
| `WEBHOOK_URL` | Прод | Адрес `/hook` для событий MAX, без него long polling |
| `WEBHOOK_SECRET` | Прод | Секрет заголовка `X-Max-Bot-Api-Secret` |
